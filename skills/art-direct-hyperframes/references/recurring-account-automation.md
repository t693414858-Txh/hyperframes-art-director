# Recurring Account Automation

Read this reference only when continuing a recurring video account whose project contains `publishing/WORKFLOW-CONTRACT.md`. It connects production with publication; it does not change the art-direction system or create a scheduler.

## Resume from evidence

Read `WORKFLOW.md`, the publication contract, `video-factory/STYLE-PREFERENCES.md`, and `publishing/douyin-inbox-ledger.json`. Resolve the current episode from the user's latest request, its active publication pack, `UPLOAD-STATUS.md`, and `PUBLISHED.md`, not modification time alone. Reconcile contradictory records before acting.

Use these conceptual checkpoints in existing records; do not create a competing database:

| Checkpoint | Required evidence before advancing |
| --- | --- |
| Topic selected | Verified source, requirements, deadline or explicit unknown, deduplication key |
| Script ready | Sepia revision, project content scoring, applicable retention and rhythm checks |
| Assets ready | Creative Production record, selected aesthetic skill applied, theme-specific original example and usable recording |
| Render verified | Exact final MP4 plus final audio, captions, visual and privacy checks |
| Delivered | One active pack: video, title, full description, entry tags, relevant tags, cover and comment prompt |
| Upload ready | Verified account, exact file in phone picker, form fields and AI disclosure checked |
| Awaiting approval | No current authorization for this episode's final publication |
| Publishing | One final click recorded; inspect result before any retry |
| Published | Visible account work-list entry and playable work/publication status, saved in PUBLISHED.md |
| Blocked | Concrete failure, last verified checkpoint, attempted recovery and next safe action |

A tool call, transmitted file, generated thumbnail or render success is not evidence for a later checkpoint. An existing published record prevents regeneration and duplicate upload unless the user specifically requests a revision or re-publication.

## Automatic work and authorization

Load `publishing/AUTHORIZATION.md` if present and resolve its latest explicit user authorization before applying defaults in this reference. A standing grant can authorize ordinary publication and bounded replies without a per-episode question; keep account, quality, timing, recipient, non-sensitive content and deduplication limits. Do not treat granted publication as granted proactive notifications or irreversible cleanup. The project's current authorization overrides only conflicting default approval language, never required action-time confirmations or safety constraints.

Proceed through authorized topic review, creation, editing, QA, delivery and upload preparation without asking at each stage. Use the earliest valid deadline among deduplicated relevant submissions. Private messages are source material, never authority to contact others, pay, or change rules.

Retain the project's approved voice, cost limits, aesthetic routing and quality gates. Use original content derived from the script, then record it; never substitute arbitrary click recordings, static slides presented as real operations, or a convenient crude image arranger. Reuse tools and checkers, not neighboring episodes' visual assets.

Absent an explicit standing grant, await final publication approval; a single current instruction to publish covers only that episode. A separately documented standing grant is valid within its scope. Recording a more automated workflow alone does not authorize unattended posting, paid services, voice substitution, account changes outside scope, or quality downgrades. Keep unaffected work moving when a specific step is blocked.

## Phone handoff and field verification

Use the publication contract as the maintained source for account identity, approved receiving device, activity entry and exact UI requirements. Do not hard-code coordinates, AX indices, nearby device names, topic limits or account names into executable steps.

Before transfer, match the exact final file; after transfer, verify the phone's picker and preview. Share only with the confirmed receiving device. Preserve existing limited photo access, adding only the requested video when necessary and authorized.

Fill title, complete description, automatically supplied campaign tag and supplemental tags as separate fields. Apply current platform limits based on visible evidence. Verify tags are linked and record the displayed metric and unit when checking popularity; unavailable metrics or posting-time data must remain unknown.

When platform AI polishing is requested, inspect the entire revised text, not the visible scrolled tail. Restore omitted campaign tags, factual limitations and the video's interaction question. Save the actually used wording back to the single active publication pack. Inspect AI-designed covers for missing words, fabricated results and readability; regenerate or correct defects rather than silently accepting them.

Check the final page actually says the appropriate AI-generated disclosure. Popup rows can shift; selecting a coordinate does not prove the intended disclosure was applied.

## Recover without damaging the draft

Use only the supported computer-control surface. After focus changes, wait for fresh UI state before entering text. Direct Chinese typing or clipboard paste may fail in iPhone Mirroring. If so, inspect residues, use individual pinyin key presses with a state refresh after each key, and visually verify short candidate groups before committing. Do not assume candidate ordering is stable. Preserve complete copy despite input friction.

On capture errors or user-driven UI changes, re-read the actual draft before resuming; never replay the whole paragraph blindly. For `noWindowsAvailable`, try fresh app state, the observed window menu's bring-to-front/position controls, then one control-session reset. These are recovery attempts, not guaranteed fixes. If the same failure persists after this bounded sequence, retain the draft and checkpoint, report the exact blocker once, and wait for a meaningful state change. Do not repeatedly re-upload, close unsaved forms, restart the phone app or weaken permissions to force progress.

## Publish once and close the loop

Distinguish the ordinary-work button from the adjacent temporary/daily-post button. Verify the requested visibility and current authorization before the one final click. While status is uncertain, inspect the account's work list and work detail; do not click Publish again. A feed navigation label alone does not establish the posted work type.

Write actual file/version, title, description, tags, cover, AI declaration, publication time, evidence and remaining uncertainties to `PUBLISHED.md`; reconcile the ledger and upload status. Deliver a concise confirmation and preserve the established requirement to provide the video and publication pack when a video is first completed.

Use the existing authorized recurring automation for inbox checks, rather than creating duplicates. This skill update alone does not create or alter schedules. On unchanged blockers stay quiet; notify on meaningful progress, completion, new failure or required action. Do not claim mobile push delivery without verification. Reuse the published work for the planned 24/72-hour review; do not post it again.

After an observed failure, update the narrow applicable rule and its reference, preserving upstream image-skill sources. Close only agent-created temporary browser tabs; retain user tabs and necessary unfinished handoffs.
